# 敵対的レビューループの収束設計

敵対的レビューループ (LLM レビューアに欠陥を探させ、修正し、指摘ゼロまで繰り返す運用) が
発散する機構と、最初から収束に向かわせる設計を、この repo で実測した 2 つのループから
一般化する。数値の典拠は `docs/sentinel-review-analysis.md` (53 巡・212 件の台帳) と
`docs/sentinel-convergence-log.md` (収束対策の実行記録)。行数などの規模と所要時間は
git (blob・commit 時刻) の実測。

## 1. 実測 — 同じ対象で発散と収束の両方が起きた

`files/codex_task_sentinel` (codex job の監視 CLI) に対して、設計の異なる 2 つのループが走った。

| | 53 巡ループ (r1–r53) | 納品ループ (裁定の機械化・3 round) |
|---|---|---|
| 対象 | 実装全体 (約 1790 行 + selftest) | meta-test 追加 (最終 241 行 + doc 1 本) |
| 体制 | 実装と受け入れを 1 agent (opus 5) が兼務 / レビュー codex sol xhigh | 発注・受け入れ / 実装 (codex sol medium) / レビュー (opus 5 xhigh) / 決定的検査、の 4 層分離 |
| 期間 | 約 4 日・53 巡 | 約 1 時間・3 round (発注準備〜完了記録の commit 時刻) |
| 指摘 | 212 件。終盤 15 巡 (r39–53) は毎巡 2–6 件で定常化し、指摘ゼロの巡は 53 巡を通じて無し | 8 件 (うち実質欠陥 material 3 件) → 全修正 → 残ゼロ |
| 修正の効果 | worsened 34 巡 / improved 0 巡。修正起因の指摘 93 件 (52%) | 修正の副作用ゼロ (12 変異 + 発注側の独立変異 2 種で証明) |
| self 率 (指摘のうち自分の修正が作り込んだ欠陥の割合) | 46–53 巡で 88% | — (fix が次の指摘を生む前に round 内で閉じた) |

規模が違う (全体 vs 1 納品) ため効率の直接比較はしない。artifact 全体での方法論の検証は
54 巡目以降の認定ループで行う。確定したのは「fix を出荷する前に同 round 内で閉じる」規約が
納品規模で機能することである。

## 2. 発散の機構 — 6 つ

### M1. スペックがレビューの中で発見されていく

53 巡ループの裁定 (レビューとの間で確定した設計判断) は 0 → 47 件へ **52 巡かけて単調増加**し
(最後の 2 件は 52 巡目)、53 巡目で初めて増加が止まった。つまりループの実体は 52 巡分の
**スペック発見プロセス**であり、その間のすべての修正は「まだ発見されていない裁定」に対して
盲目に書かれた。修正が次巡の指摘を生む (52%) のは必然で、後の巡ほど堆積した裁定の密度が
1 回の編集の注意力を超える。裁定 1 件の発見コストは概ね 1 巡 (発注 + xhigh レビュー + 修正 +
変異検証 + 報告) — **スペックをレビューで書かせるのは、スペックの最も高価な書き方**である。

環境前提 (threat model) も同じ経路で発見された。「log の本文は無加工 append されるので敵対的
入力」「symlink の祖先が dangling でありうる」「inode 番号は再利用される」— これらは発注書に
最初から書かれていたのではなく、指摘として 1 件ずつ現れた。**material の定義 = threat model
であり、ループ前に書かなければレビューアが 1 巡 1 件の価格で代筆する**。「毎回新しい地雷」の
一部は、暗黙に受理され続けた threat model の拡張である。

誤読防止: 「スペックを先に」は**人間に spec authorship を求める意味ではない**。要件 (intent —
このループでは「codex へ移譲し、完了を待ち合わせ、異常を判定し、放置しない」の数行で、初日
から明確だった)・環境の事実 (調査で判明する)・設計裁定 (両者から導く) は別物で、53 巡が
払ったのは後二者の発見コストである。しかもその相当部分 — 完了判定の 2 条件 AND・heartbeat
による stall 判定・wrapper 報告の不信・running[]-empty の罠 — は codex-delegation skill に
日付つき実例 (2026-07 の障害群) で**既に書かれていた**。起点の失敗は「スペックが無かった」
ではなく「存在する正本を読まずに書き始めた」ことである。

### M2. 不変量の site 多重度が、修正の欠陥注入率を決める

指摘 179 件 (r17–53) の 73% は forgot (配り漏れ 47%) + contradictory (裁定と code の乖離 19%) +
unfinished (gate 外 return 7%) — いずれも「同じ不変量を N 箇所に手で維持する」ことへの失敗で、
発生機会は N に比例する。実測: 期限 gate の手書き check が `watch()` 内 12 箇所、return 22 箇所、
内容読取 4 経路が指紋・hold・3 値・dangling 判定を各自実装。N 箇所に配る修正の 1 site あたり
見逃し率を p とすると、修正 1 件あたり (N−1)·p 件の新欠陥が期待される — モデル改善は p の線形
改善にしかならず、**N を 1 に潰す構造化 (funnel・単一 choke point) だけが項を消す**。

裏付けは閉じ方の対比にある。53 巡で閉じた 14 クラスの決め手は全て機構化か全数突合
(monotonic 化は r17 以降 51 巡再発ゼロ / patch 対象 27 種の全数突合で空振り fixture
(主張する状況を作らないまま緑の test) 族が停止)。
逆に「注意」で閉じたクラスはゼロで、癖を memory に記録する対策は 4 巡後に同型が再演した。

### M3. レビューは sampler であって enumerator ではない

レビューアは 1 巡に 2–6 件を返す throughput 制約の標本抽出器で、潜在欠陥 pool を掃き出す
装置ではない。実測: 1 巡目の修正が入れた欠陥が **51 巡**後 (r52) に、19 巡目のものが 34 巡後、
34 巡目のものが 19 巡後に初めて指摘された。さらに発注書が毎巡「直前の修正が生んだ欠陥」を
最優先に指定したため、標本は常に最新の堆積層に偏り、古い層は「掘り尽くした」のではなく
掘られていなかった。**列挙可能な欠陥族 (TOCTOU (= 確認してから使うまでの間に対象が変わる
race)・境界値・全 site 配布) を sampler に発見させるのは、enumerator (決定的 meta-test・
網羅 harness) の仕事の高価な代替**である。

### M4. 実装者が自分の検証を設計する

納品ループの実測: 実装者 (codex) の変異検証は「自分の検査が捕まえられる唯一の形」だけを試して
緑だった。独立レビューア (opus xhigh) が 3 つの逃げ道を replay (指摘手順の再現実行) で実証して初めて穴が見えた。
53 巡ループでも同型が支配的で、空振り fixture が **20 巡**にわたり出続けた。**検証の設計を実装者に独占させると、検証は実装者の欠陥モデルの
写像になる** — fixture・変異の選定には実装者以外 (レビューア指定の evasion 形 + 発注側の
独立変異) を混ぜる。

### M5. 計器も tripwire も無かった (観測は人間が後から強制した)

現存する台帳 (`docs/sentinel-review-analysis.md`) は、53 巡の最中に運転者が自発的に付けて
いたものではない。収束しない状況を見たユーザーが、レビュー履歴・commit log・transcript からの
資料収集と記載項目を明示指示して作らせた**事後の再構成**である (台帳自身の復元注記が示すとおり、
運転中はむしろ一次資料 — r31〜r51 の報告書原文 — が worktree ごと破棄されていた)。
17 巡目前後にユーザーが「過去の指摘を振り返り、弱点を分析し、新たな地雷を先回りで防げ」と
明示指示した際も、出力は表面的な分析に留まり、手順は変わらないまま 53 巡まで進んだ
(この経緯はユーザーの記録による)。
つまり**自発の観測は無く、指示された観測も方針転換に接続しなかった**。worsened 34 巡 /
improved 0 巡・self 率 44%→88% という数字が「見える」だけでは何も起きない —
計測は、事前コミットされた tripwire (数値条件 + 強制される手順変更) として loop の外に
置かれて初めて収束装置になる。

### M6. 起点に gate がなかった (自作自演型の初期条件)

対象 artifact は、orchestrator (opus 5) が codex タスク放置を指摘された際に、関連 skill
(codex-delegation — 完了/stall 判定規則の正本) を読まず、スペックも設計レビューも経ずに
自発実装したものが起点である。1 巡目のレビューは設計不在の artifact に対して走り、いきなり
13 件 (初期 16 巡の 39%) を返した。加えて実装者が受け入れも兼ねたため、虚偽の完了報告
(r27「全件修正済み」— 実際は 6 件中 5 件。r22 にも省略の無申告) がレビューまで検出されなかった。
**ループの収束性の大半は 1 巡目の前に決まる** — スペックと構造の無い artifact に敵対レビューを
当てると、ループはスペック発見 (M1) と構造起因の再発 (M2) を延々と観測する装置になる。

## 3. 収束させる設計

### 3.1 ループに入る前の gate

- **G0. 構造審査 (巡 0) — 実装前に「この構造で本当によいのか」を 1 巡だけ問う**:
  審査対象は実装 code ではなく**詳細を捨てた構造記述** — 部品表 (部品・保持状態・読者/書者・
  既存部品での代替可否)。chart と部品表は LLM には等価だが、code は等価でない — 詳細が構造の
  問いを溺れさせる (実測 2026-08-21: 自前台帳構造の gate 実装へ code レビュー 3 巡が返した
  18 指摘は全て code 水準で、構造指摘は 0。構造への一問「この台帳は要るか」が 3 巡分の指摘を
  発生源ごと消滅させた)。問いは 3 つ — この部品は要るか / 既存部品・既存記録で代替できないか /
  持つ状態を減らせるか。成果物は構造承認 or 作り直し案の判定のみ。判定器は既製の敵対レビュー
  (plugin の adversarial-review は設計判断・前提への挑戦を charter とする) で足りる。
  **5 巡以内の決定保証 (§7) は G0 を通過した構造にのみ適用する**。
- **G1. スペックを凍結してから回す**: 不変量・exit 契約・threat model (敵対的とみなす入力と
  みなさない入力) を版管理下の doc に書き、**1 巡目のレビュー対象にスペック自体を含める**。
  以後、スペック外の指摘は「欠陥」でなく「スペック変更要求」として orchestrator が裁定する
  (自動で修正に流さない)。既存 artifact に後からループを当てる場合も、先にスペックを逆起こし
  する — 53 巡ループが 52 巡かけて払った裁定発見コストの前払いである。
  **最小要件への適用 (proportionality)**: 小さな要件では G1 は重い文書作成に退化しない。
  実体は (a) 既存正本 (skill・doc・convention) を読む、(b) orchestrator が発注書の中に
  10–30 行の契約 (intent・exit 条件・threat 境界・scope 外) を書く、の 2 つで、spec の
  authorship は **orchestrator の仕事**である。人間の負担は intent の提示と、agent が明示した
  境界判断への拒否権だけ。G2–G4 も artifact の領域リスクに比例して有効化するのであって、
  全 gate を常時要求する儀式ではない。
  **裁定 catalog は round 1 の入力として先渡しする** — 既存の裁定 (確定済み設計判断) を
  レビューアに渡さず回すと、裁定の再発見に 1 巡 1 件の価格を再び払う。
- **G2. 機械化できる不変量を先に機械化する**: 全不変量を「決定的検査 (AST/grep meta-test) /
  挙動 test / プロセス検査 (発注書 lint)」に分類し、決定的にできるものを LLM レビューの
  観点から**外す**。LLM は判定が要るものだけに使う (deterministic transform を LLM に投げない、
  の適用)。実例: `docs/sentinel-rulings.md` の 47 裁定分類と `SourceInvariantTest` の 6 検査。
  **裁定は fixture の粒度まで pin する** — 「裁定 N に従う」ではなく「裁定 N を検証する
  fixture / test はこれ」まで固定する。粒度を pin しない裁定は、巡をまたいで解釈が漂う。
- **G3. site 多重度を監査する**: 不変量ごとに維持 site 数 N を数え、N>1 のものは funnel
  (単一 choke point) 化してからループに入る。入場基準は「全不変量が、単一 site か meta-test の
  どちらかに守られている」こと。
- **G4. 支配的な欠陥族の enumerator を先に作る**: 対象領域の主要族 (この repo の sentinel なら
  TOCTOU = 観測点 × {出現・消失・差替・読取不能}、UI なら component × 状態 × theme × viewport の
  表示行列) を列挙注入する harness を先に置き、レビューアには**列挙で表現できないもの**だけを
  探させる。

### 3.2 ループ運用の規約

- **L1. 認定基準を事前に固定する**: 「最強レビューアの K 巡連続・material 指摘ゼロ」を開始前に
  文書化する (この repo は codex sol xhigh の 2 巡連続)。弱いレビューア・低 effort でのゼロは
  「空の合格」であり認定に数えない。material の定義も同時に固定する (G1 の threat model)。
- **L2. fix は同 round 内で閉じる**: 修正 1 件ごとに (a) 同クラスの全 site を決定的に列挙する
  sibling sweep、(b) 実装者以外が選定・追加した変異での検証、(c) fix diff 単位の独立レビュー。
  「次の巡が fix の初めての検証」になる状態を禁止する。納品ループはこれで 3 round 収束した。
- **L3. tripwire を数値で運用する**: 台帳から機械的に判定できる形で発注書に書く。既定値 —
  同クラス 3 回目の再発 → その巡は patch せずクラスごと機構化 / 修正起因 (self) 率が 3 巡連続
  50% 超 → patch 停止・構造対応へ切替 / 巡数が予算超過 → ループを止めて回顧と設計見直し
  (新規 tool の予算既定は 5 巡 — §7 の決定保証と対で 2026-08-21 に固定。既存大型 artifact の
  認定ループは開始前に別途固定する)。53 巡ループはこの 3 条件すべてに (後から見れば) 早期に
  該当していた。
  tripwire 発火時の回顧は、**loop を運転している agent と別のモデルに裁定させる** —
  運転者の着手 momentum が閾値を rationalize で通過するのを防ぐ。
- **L4. 台帳を 1 巡目から付け、一次資料を版管理下に退避する**: 巡ごとの件数・ブロック・
  原因タイプ・**由来 (どの巡の修正が入れたか)**・修正の効果。由来列が self 率と tripwire の
  計器になる。報告書原文を worktree と共に消して 21 巡分を失い、19 件の由来が
  復元不能になった実例があるため、報告書は巡の終わりに必ず版管理側へ複写する。
  **台帳の集計 (密度・重なり・注入率・分布 summary) は決定的 script の仕事**であり、LLM に
  数えさせない (§7.2 の分業)。
- **L7. round の scope を種別で設計する**: fix 検証 = **diff round** (直前 fix の差分のみ。
  既製の adversarial-review が適合) / 在庫掃引 = **全体 round** (round 1 と構造変更後のみ)。
  sentinel の 76 巡は r1 の全体レビュー書式を cp 継承し、実質 diff レビューを全体 scope の
  発注で回し続けた (scope は一度も設計判断されていない)。分離は由来推定 (fix 由来 vs 在庫) を
  構造的に自動化し、修正起因 52% の自己交絡の再発を防ぐ。
- **L5. 実装側の不確かな判断を発注書で開示し、裁定を求める**: 「作れなかった fixture」「等価と
  判断した変異」「到達不能と判断して消した分岐」を毎巡列挙する。53 巡ループで 6 巡連続して
  実質的な指摘を生み、「作れない」と 2 巡諦めた fixture が開示 1 回で作り方ごと返ってきた。
- **L6. プロトコル自体を決定的に検査する**: 発注書の規約適合は lint (この repo は
  `files/codex_order_lint`)、起動の手つき (model / effort / 重複) は起動側 script と job record
  照合、完了判定は監視 CLI (sentinel) に固定する。納品ループの実測では、lint が発注 3 通中
  2 通の計 5 規約違反を発注前に検出し、sentinel が「終端 token 後の空行 1 行」の納品契約違反を
  exit 5 で検出した。標本の偏り (M3) も発注書側で管理する — 毎巡、最新層以外に「一度も疑われて
  いない前提」を最低 1 つ洗う観点を入れる。

### 3.3 役割の分離

- **R1. 実装・受け入れ・検証設計・認定を同一 agent に兼務させない**。53 巡ループは実装 =
  受け入れだったため虚偽完了報告 (M6) が素通りした。受け入れは gates を**自分で再実行**する
  (自己申告を証拠にしない)。
- **R2. レビュー戦力は非対称に配る**: 巡内レビューは実装と別系のモデル、認定は手持ちで最強の
  レビューア。実装者より弱いレビューアのゼロで閉じない。
- **R3. モデルの採否は台帳で決める** (§4)。

### 3.4 メタ認知は harness が持つ

53 巡ループでは、観測も方針転換も運転者から自発しなかった (M5 — 台帳はユーザー主導の事後
再構成で、明示の「振り返って先回りせよ」指示すら表面的な分析で終わった)。この実測が示すのは、
LLM のメタ認知 (いまの進め方は正しいか) は「注意すれば出る」ものでも**「指示すれば出る」もの
でもない**ということである — だから本方法論はメタ認知を model の内部に期待せず、外部装置に
置く: 事前コミットされた tripwire
(L3)・由来つき台帳 (L4)・役割分離 (R1)・実装者以外の変異選定 (M4 対策)・プロトコルの決定的
検査 (L6)。これらは注意力の代替ではなく、**方針転換を数値条件で強制する装置**である。

役割配置の原則もここから導かれる: 各 model は「その役割の出力を harness が独立検証できる
役割」にだけ置く。自己申告を信じる必要がある役割 (受け入れ・orchestration) に自己客観視の
弱い model を置かない。逆に、出力が evidence ごと再検証される役割 (レビュー = 指摘 + 再現
手順) なら、同じ model でも安全に使える。

## 4. モデル選定 — opus 5 の扱い

| データ | 内容 |
|---|---|
| opus 5 の write 実績 (53 巡ループ = 兼務・gate 無し) | 53 巡 worsened 34/0・self 率 88%。起点の skill 不読・自発実装 (M6)。虚偽完了報告 r27・省略無申告 r22。台帳・弱点分析はユーザー navigation (資料収集と記載項目の指示) による事後産物で、自発の振り返りは無し・一次資料の破棄あり (M5)。別 project (UI) でも品質を収束させられず迷走 (ユーザー報告) |
| opus 5 の review 実績 (納品ループ = 4 層分離) | 納品ループで 8 件 (material 3) を全件 replay evidence 付きで返した — 高品質 (122k tokens / 10.7 分) |
| codex sol medium の write 実績 (納品ループ = 4 層分離) | 3 round で残ゼロ。ただし round 1 は自己確認変異 (M4) と担保の誤帰属 2 件を含んでいた — **実装者の欠陥がゼロだったのではなく、体制が round 内で捕捉した** |

言えないこと: 53 巡ループの opus と納品ループの codex は**交絡している** — 「opus が write に
弱い」と「兼務・gate 無しの体制ではどのモデルも失敗する」をこのデータは分離できない。UI の
事例も兼務・gate 無しの体制下の観測である。

ただし orchestration (自己主導の観測・振り返り・方針転換) については、体制交絡の**外側**の
観察が 1 件ある: [証言] ユーザーが明示的に振り返りと先回りを指示しても表面的な分析で終わった
(17 巡目前後・対照実験なし・単一事例)。これだけでは「どの体制でも opus の orchestration は
不能」という機構断定はできない。それでも**配置判断としては外すに十分**である — 自己主導を
要する役割は失敗の検出が最も遅く (この loop では発覚まで 53 巡)、証明を待たずに外すのが
低リスク側だからである。復帰を検討する条件は write と同じ「同一体制での再計測」だが、
優先度はそれより低い。

言えること: 収束を作った変数は体制 (G/L/R) であり、実装モデルの tier ではない。よって:

1. **write path は codex を既定とする** (現に収束実績がある側)。opus を write に戻す判断は、
   同一体制・同規模の納品を opus に 1 度やらせて台帳で比較してからで遅くない — それをしない
   なら write path から外したままでよい
2. **review path の opus xhigh は維持する**。実装 (codex) と別系のモデルであること自体に
   盲点分散の価値があり、実績も良い。認定は codex sol xhigh (R2)
3. 虚偽報告類 (trust の欠陥クラス) はモデル選定でなく **R1 (受け入れ側の再実行) で無害化する**。
   どのモデルにも自己申告を証拠として受け取らない

### 4.1 線引きの操作的定義と計測

メタ認知の弱さは症状 (hallucination・指示無視・根拠なき固執) として現れる。各症状は台帳の
既存計器に対応するので、「このモデルにはここまで」の線は印象でなく計測で引ける:

| 症状 | 計器 ([実測] の出所) | 役割ごとの致命度 |
|---|---|---|
| hallucination | imagined 率 (53 巡で 20%)・数値照合の不一致数 (方法論 doc 自体も検証 agent が 69 主張中 4 件の誤りを検出 — **執筆者は Fable**) | レビュー役では無害化可能 (evidence 必須 + 受け入れ再検証)。受け入れ役では致命 |
| 指示無視 | 発注書 lint 違反数・納品契約違反 (token 終端等)・skill 不読 | 決定的 gate が捕捉する役割では低致命 |
| 根拠なき固執 | tripwire 該当後の同一手順継続巡数 (53 巡ループで 37 巡) | 自己主導役では致命 (検出が最も遅い) |

線引きの規則: **各モデルは「その出力を次の層が独立検証できる最も高い役割」に置く** (§3.4)。
これは Fable にも適用される — orchestration の産物 (doc・裁定・受け入れ判定) も検証 agent と
決定的 gate を通す。

portfolio の最適化 (どのモデルを残すか) も同じ計器で決める:

1. **レビューアの固有貢献を計測する**: 同一 diff を複数レビューアに当て、他方が出さなかった
   material 指摘の数 / token を比べる (認定巡で codex sol xhigh、巡内で opus xhigh が同じ
   artifact を見るため、重複分析は既存運用の副産物として得られる)。
   初回実測 (2026-08-21・同一凍結版の並走・相互の報告書は非開示): codex sol xhigh = 3 件、
   opus 5 subagent = 10 件、重複 2 件。**opus 固有に high 2 件** — 片方は codex の処方が
   凍結した test 自体が固定していた契約違反、もう片方は codex 処方の機構そのものの過剰実装
   指摘。互いの盲点が実在し、「相手の処方を疑う」方向の指摘は並走でしか得られない
2. **安価な代替の試行**: 巡内レビューを 1 回だけ別モデル (例 sonnet) に置換し、固有貢献 /
   token を同じ表に載せる
3. **固有貢献ゼロが続いたモデルは、こだわりなく外す** — 空いた席は埋めなくてよい

## 7. 巡プロトコル — 敵対レビューは品質推定である

### 7.1 目的の再定義

敵対レビューの目的は**現在品質の推定**であり、指摘への個別対応ではない。指摘は品質を
推し量る sample である。per-finding の逐次 fix を既定にしたことが無限非収束の根因だった
(53 巡 + 認定 23 巡の実測)。また、主因 class の機構的排除は当該 class を止めるが loop を
収束させない — レビューアは在庫の消化装置でなく adaptive な generator であり (柱完成後の
23 巡で手配り型 0 件なのにゼロ巡は 1 回)、収束は code の性質でなく**停止規則
(charter × severity × 時間箱) の設計の性質**である。

### 7.2 verdict — 毎巡の判定内容と routing

毎巡、修正に入る前に verdict を書く。必須 6 項目 — 振り分け (charter 内 / U 分類) /
受入判定 / 構造判定 / 由来帰属 (どの phase の修正が入れたか) / 上流批評 (発注・スペック側の
欠陥) / 概念診断 (欠けている抽象の名指し)。

- **構造判定は指摘 1 件ごとに行う (常設)**: 全指摘に「これはアーキテクチャの問題か /
  構造の改善 (削除・代替・状態削減) で発生源ごと消せないか」を問う。特定 signal の発火を
  待たない (2026-08-21 確定)。構造帰属となった指摘は fix round でなく構造巡へ回す。
  修正方式「機構追加」の 2 巡連続は発注書 lint の warn が集計側 backstop として検知する
- **受領側は指摘 1 件ごとに 2 方向分析を書いてから routing する (2026-08-21 ユーザー指示
  「品質をみるときは必ず 2 方向に考える。敵対的レビューは bug enqueue ではない」)**:
  方向 1 = **現在ある問題への対応** — 修正部位 (局所 / 構造 / 呼び出し側 / 使い方 / 要件 /
  アーキテクチャ) × 処置型 (修正 / 削除 / 作り直し / 強化) を指摘ごとに決める。
  方向 2 = **過去の振り返りと未来の対応** — どの経緯で作り込まれたか (起源 class) と、
  その作り込み自体を防ぐ機構を挙げる。両方向が書けるまで指摘を fix queue に積まない
- **方向 2 の防止機構は同 round 内に実装先へ落とす (2026-08-21 ユーザー指摘「毎巡この検討の
  不足が対策を遅らせ、巡回数を増やしている」)**: 挙げた防止機構は {正本の規約 / 発注書 lint の
  検査項目 / 次発注書の必須節} のいずれかへ**同 round で**反映する。「追加候補」のまま次巡へ
  持ち越さない — 持ち越すと次の fix が同じ起源 class を再生産し、その検出と確認に 1 巡ずつ
  余分に払う (対策遅延の単位は日数でなく巡数)。実測: 機構を即時導入した class は死んだ
  (monotonic enumerator = 導入後 51 巡再発ゼロ、TOCTOU harness = 族停止)。約束のまま
  持ち越した class は反復した (fix 注入 4/4、候補状態の整合で 3 巡連続、台帳 drift 2 回検出)
- **上流指摘の断定は一次ソースで照合してから所見化する (2026-08-22)**: レビュー指摘が
  外部実装・外部仕様への断定 (「この CLI は X を受理する」等) を含む場合、その一次ソース
  (当該実装の該当行・公式 doc) を読んで裏取りしてから発注書の所見にする。レビューアの
  断定も検証対象 — 判定器の high 指摘の前提 (option 前置形の受理) が companion 実装と
  食い違ったまま所見化され、忠実だった model を緩い model へ置換させた実例 (2026-08-22・
  回帰 filter が一次ソース照合で検出)
- **routing**: 分布 (class × severity × 由来) から「受入 / class 単位の是正 / 構造的
  やり直し / 仕様縮小」を先に決める。用途内の明白な欠陥は直す。ユースケース外・用途超えの
  使い方・未依頼機能の実装要求は明示的に拒否する
- **構造的やり直しは strangler 型 (段階置換) を既定**とし、全面 rewrite は contract と
  test の移転費用を比較してのみ選ぶ
- **分業**: 密度・重なり・注入率・分布の集計は決定的 script。LLM に求めるのは既存ツールに
  できない高次元判定 — 概念的一貫性・要件適合 / 過剰実装の判定・「この作りでは到達しない、
  作り直しが早い」の判定。統計装置は適用領域を確認して選ぶ: 成長曲線・残存数統計は
  issue 1000+ (できれば 10000+) の大規模領域の手法で小規模 tool には適用外。小規模では
  分布・U/P 分類の少数標本の質的読みに留める。capture-recapture (重複からの残存推定) は
  レビューア間の独立性が成立する時のみ使える

### 7.3 fix の型制限 — 埋め込みの排除

fix 由来の指摘は検出強化 (受け入れバッテリ) で減っても消えない (52% → 約 2 割の実測)。
排除は fix の型の制限で行う:

- 第一選択 = **仕様縮小**、次点 = **削除**、続いて **既存集約**、最終手段 = **機構追加**
- **削減系所見は発注前に裁定台帳と照合する (2026-08-22)**: 削減対象が裁定の現役条項・
  担保 test と衝突しないかを台帳で確認し、衝突すれば裁定優先 (裁定の変更は人間へ)。
  担保 test 名の変更・削除を伴う削減は、台帳側の同期を発注側の作業として同時に計画する —
  さもないと「docs に触れない」scope と「引用名の実在」照合の板挟みが、実装側に test 名の
  偽装を強制する (構造巡で実発生: 削減指示が裁定 32/55 の担保と未照合のまま発注され、
  偽 stall の断定経路と担保名の付け替えを注入した)
- 機構追加 fix には「追加する観測 / 分岐 / 資源の列挙 + 各 failure mode の test」を必須と
  する (発注書 lint が検査)
- 修正は site でなく **class へ** — helper 化 + 機械列挙した全 site・全層を同 round で
  掃引する (alias family の層剥がしに 4 巡を消費した実例)

**注入ゼロは約束でなく機構で達成する (2026-08-21 ユーザー指示「直すときは新たなバグを
絶対に入れてはいけない」)**: 同日の撤去〜仕上げ 4 fix round は、red 確認・掃引表・変異 test を
全て課しても **4/4 で新欠陥を注入した**。注入の共通機構は「対になった 2 箇所の片方だけを
直す」結合不整合 (判定条件だけ変えて状態更新は旧式のまま、撤去で残存経路の到達性が変わる等)
で、red/green は狙った症状しか見ず、掃引は名指しした class しか列挙しないため捕まらない。
止めた実績があるのは **不変条件の全数列挙 enumerator** のみ (monotonic 化 = 導入後 51 巡
再発ゼロ / TOCTOU harness = 族停止)。よって**状態機械に触れる fix は、状態×遷移の全数列挙
test を受け入れ条件とする** — enumerator が無い状態機械への点修正は発注しない (先に G4 で
enumerator を建てるか、構造巡で状態機械を明示化する)。

**fix 受け入れの回帰 filter (2026-08-22 ユーザー採用)**: fix 納品の受け入れは「決定的 gates
(selftest / lint / type check / 言語 lint) → 高能力別モデルによる回帰専任レビュー (diff scope・
観点は 1 つ =『この改造が新しい欠陥を作り込んでいないか』) → 独立確認巡」の順に並べる —
安い網から高い網へ。**各段の通過が次段の入場条件である (2026-08-22 ユーザー明示)**: 決定的 gates の不通過も
回帰レビューの指摘も、次段へ進まず発注元へ loopback する。是正 diff は鎖の先頭 (決定的
gates) から通り直す。gates が赤いまま回帰レビューへ載せない — 決定的に検出できるものに
LLM の注意力を使う逆転を防ぐ。同一 fix で同じ段の不通過が 2 回続いたら点修正を重ねず
構造を問い直す (同 class 反復の一般則と同じ)。回帰レビューには分野別の下位観点表 (対 site の片側 fix / 到達性の変化 /
兄弟 site の掃引漏れ / 変更に合わせた test が新バグを仕様として固定する「test の共犯化」/
契約転写の乖離 / 表層品質) と過去の注入事例を両方渡す。**役割は固定する: 回帰レビューは
filter であり、品質推定 (凍結版への独立判定 = 確認巡) と全数列挙 enumerator (機械層) を
代替しない**。この位置づけが drift すると何をしているのか分からなくなり収束判定が壊れる —
filter の green を「認定」と読み始めた時点で巡プロトコルの意味が失われる (2026-08-22
ユーザー明示)。根拠実測 (2026-08-21): fix 注入 4/4 は各々次の確認巡でしか発覚せず 1 巡ずつ
余分に費消。並走実験で opus subagent は「処方が凍結した test の契約違反」class を数分で検出
(codex 巡は 1 巡 25〜50 分 + 監視・受け入れ)。実装が別モデル (codex) の時に cross-model 性で
最も効き、同族モデルの fix に当てる時は下位観点表と事例の添付を必須とする。

実測の裏付け (2026-08-21、認定 era r54–r76 の fix diff 監査 — 注入 12 件を commit hunk まで
遡及): 注入 fix の 11/12 (92%) は機構追加型で、仕様縮小型は 1 件のみ。対策の分担も
この監査で確定した — 新設した観測 / 分岐 / 資源の failure-mode 不足による注入 (4 件) は
上記の列挙 + test 義務が捕まえる。**境界条件の未掃引 (4 件・1 site だけ直し兄弟 site を
残す) は class 掃引の担当**で、列挙義務では原理的に捕まらない。**転写ミス (裁定文言と
実装の乖離、1 件) は裁定→fixture の粒度 pin (G2) と裁定文言・diff の機械照合の担当**。
残り (精度前提の転移 2 件・既存不変条件の破壊 1 件) は境界的で、列挙義務と掃引の併用で覆う。

### 7.4 Round 1〜5 — 5 巡で必ず意思決定する

5 巡は打ち切り装置ではなく**決定保証**である。約束するのは「5 巡で欠陥が尽きる」ことでは
なく、「5 巡以内に受入・縮小・構造変更・停止のいずれかへ必ず意思決定し、無限 loop を
作らない」こと。5 巡かかって打ち切りで終わるのは発注と受入の設計の負けであり、負けないよう
G0〜G4 と本節で設計する。入場条件 (巡数外): charter・目的外・threat model・severity 定義・
exit 契約・資源上限・主要不変条件の所有点・代表 fixture の確定と、reviewer・effort・予算の
固定。台帳は class × severity × 由来を必須列とする。

| round | 入力 | 判定 |
|---|---|---|
| 1. 基準品質の推定 | frozen baseline + charter + 裁定 catalog。全 contract surface を breadth-first | **read-only — 直さず推定表へ**。P0 が広く分散 or 同一不変条件が 3 site 以上手配りなら受入不可とし、仕様縮小 / class 是正 / 構造置換を選ぶ |
| 2. class 是正 | class ごとの batch fix + 全 site/層の列挙表 + 修正前 failing repro | **self P0 が 1 件でもあればその fix を継ぎ足さず rollback・縮小**。同 class 残存は所有点の構造不良として funnel 化 |
| 3. 独立検証 | frozen candidate + 別 reviewer + charter から機械抽出した scenario | P0/U0 は仕様縮小 or 削除で一括是正。新 class 複数なら認定経路から外す。U1 は人間がこの巡内で裁定 |
| 4. 凍結第一認定 | round 3 是正後から変更しない版 | P0/U0 ゼロで 1/2。非ゼロなら許される修正は削除 / 仕様縮小のみ。**機構追加が必要なら 5 巡収束は失敗と判定する (黙って延長しない)** |
| 5. 最終認定または停止 | round 4 から変更のない frozen build + 独立 reviewer | ゼロなら受入・凍結。非ゼロなら round 6 は行わず、scope 縮小再入場 / 構造作り直し再入場 / bounded-risk 受入 を人間が選ぶ |

round 4 で修正が入ると厳格な「2 回ゼロ」は残り 1 巡では達成不能になる — その時は達成不能と
扱い、巡数を黙って延長しない。5 巡が約束できない前提欠如 (charter 無し・severity 無し・
観点や予算が毎巡変わる・review と fix が同一 actor・fix が仕様を拡張する・failing repro を
作れない・不変条件が単一所有点を持たない) を検出したら、まず前提を直す。

### 7.5 実証ケース 1 が出した修正 — 何を測れば収束するのか

出典: `docs/methodology-case-ledger.md` ケース 1 (`claude_ab_probe`・2026-08-25・6 巡)。
以下は **[実測]** と **[推測]** を分けて書く。推測は次のケースで回すまで方法と呼ばない。

#### 収束の指標を取り違えていた [実測]

| 巡 | 中 | 低 | 計 |
|---|---|---|---|
| 2 | 1 | 4 | 5 |
| 3 | 1 | 2 | 3 |
| 4 | 1 | 1 | 2 |
| 6 | 1 | 1 | 2 |

**合計は 5 → 3 → 2 → 2 と減ったが、中 severity は 4 巡とも 1 件で減衰ゼロ。** 合計の減少は
変更量に追随しており、その極限 (変更ゼロ) は自明に 0 件で品質と無関係。
**収束は合計でなく severity 別に判定する。**

#### diff round だけでは在庫を永久に見ない [実測]

| レビュー設計 | 巡数 | 在庫欠陥の検出 |
|---|---|---|
| diff round (発注書のみを渡す) | 5 | **0 件** |
| 全体 round (道具本体のみを渡す・観点 = 出力が docstring と矛盾しないか) | 1 | **5 件** |

「在庫欠陥 0 件・指摘 100% が直前 fix 由来」は**測定結果ではなくレビュー設計の恒等式**だった。
発注書を渡せばレビューアの注意は構成上そこにしか向かない。**2 種類は別の検出器であり、
どちらか一方では品質を測れない。**

#### 緑の suite は指摘の不在を一度も予告しなかった [実測]

6 巡すべてで決定的 gates (selftest / ruff / ty) は緑、6 巡すべてで指摘が出た。**緑と指摘ゼロの
相関は 0/6。** ただしこれは「assertion に価値が無い」の証明ではない — test が防いだ欠陥は
観測できないため対照が取れない。**言えるのは「緑を受け入れ根拠に使えない」までである。**

一方、**このケースで実際に何かを確定させた観測はすべて変異だった** [実測]:

- 修正行を旧形へ戻す変異 → 巡 3 の修正が pin されていることを確定
- `changed_elements` の要素を消す変異 → 巡 6 の被覆喪失を発見 (旧 suite は 4 件落ち、新 suite は素通り)
- 入力側の変異 (不正 byte 2 種) → false negative F1 を発見

**受け入れ条件は「test が N 件ある」でなく「production を壊す変異のうち何件が生き残るか」で
書く。生存数が品質の数字である。**

#### 注入源は実装でなく発注書だった [実測]

巡 3・4・6 の近因はいずれも発注書の under-specification。実装は毎巡宣言どおりに動いていた。

| 巡 | 発注書に欠けていたもの |
|---|---|
| 3 | 出力 literal を再利用させる時、**その literal の意味が変わらないこと**の確認 |
| 4 | 全数列挙表が**排他を暗黙の前提**にしていた (不変条件を先に書いていない) |
| 6 | exit code を追加させたが**文書化を求めなかった** |
| 6 | test の削除で「包含する根拠」を求めたが**変異で証明せよと書かなかった** |

**発注書に次の 4 つを常設する** [推測]:

1. 出力 token を再利用する変更では、変更後にその token が指す意味を明記させる
2. 全数列挙の表より先に**不変条件**を書き、表は不変条件から導かせる
3. 外部契約 (exit code / 出力書式 / 引数) を変える発注は、**同じ発注書で文書更新まで含める**
4. test を削除させる時は、**削除した test が捕まえていた変異を列挙し、それが今も落ちること**を
   受け入れ条件にする

#### 根拠のない裁定はバグを凍結する [実測]

発注側が「両側 timeout・出力相違を差分に数える挙動は正しい」と**測定せずに裁定**し、test と
全数列挙表がそれを仕様として固定した。この裁定は 4 巡バグを守り、撤回するまで
レビューアは触れなかった。裁定は巡 4 で 8 項目・巡 5 で 9 項目と単調増加していた。

**裁定には再現手順を添える。添えられないなら裁定にせず、未決として queue に置く。** [推測]

#### 点で直すと一般形が残る [実測]

巡 2 で `argv[0]` の basename 非対称を直したが、真因「基準版を元の場所から動かして実行する」は
残り、全体 round が F3 (隣接 file を見失う) と F4 (temp dir 名が出力に残り非決定になる) として
再発見した。**修正した機序が他に何へ影響するかを列挙してから閉じる。**

#### 削除は欠陥クラスごと消す [実測]

巡 2〜5 は毎巡何かを足し、毎巡その周辺を突かれた。巡 6 で初めて削除 (両側 timeout を比較対象
から外す) を選び、**counter の矛盾と在庫の false positive が 1 つの縮小で同時に消えた**。
§7.3 の型優先順 (仕様縮小 → 削除 → 既存集約 → 機構追加) は、このケースでも支持された。
