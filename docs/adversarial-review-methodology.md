# 敵対的レビューループの収束設計

敵対的レビューループ (LLM レビューアに欠陥を探させ、修正し、指摘ゼロまで繰り返す運用) が
発散する機構と、最初から収束に向かわせる設計を、この repo で実測した 2 つのループから
一般化する。数値の典拠は `docs/sentinel-review-analysis.md` (53 巡・212 件の台帳) と
`docs/sentinel-convergence-log.md` (収束対策の実行記録)。行数などの規模と所要時間は
git (blob・commit 時刻) の実測。

## 1. 実測 — 同じ対象で発散と収束の両方が起きた

`files/codex_task_sentinel` (codex job の監視 CLI) に対して、設計の異なる 2 つのループが走った。

| | 53 巡ループ (r1–r53) | 納品ループ (裁定の機械化・3 round) |
|---|---|---|
| 対象 | 実装全体 (約 1790 行 + selftest) | meta-test 追加 (最終 241 行 + doc 1 本) |
| 体制 | 実装と受け入れを 1 agent (opus 5) が兼務 / レビュー codex sol xhigh | 発注・受け入れ / 実装 (codex sol medium) / レビュー (opus 5 xhigh) / 決定的検査、の 4 層分離 |
| 期間 | 約 4 日・53 巡 | 約 1 時間・3 round (発注準備〜完了記録の commit 時刻) |
| 指摘 | 212 件。終盤 15 巡 (r39–53) は毎巡 2–6 件で定常化し、指摘ゼロの巡は 53 巡を通じて無し | 8 件 (うち実質欠陥 material 3 件) → 全修正 → 残ゼロ |
| 修正の効果 | worsened 34 巡 / improved 0 巡。修正起因の指摘 93 件 (52%) | 修正の副作用ゼロ (12 変異 + 発注側の独立変異 2 種で証明) |
| self 率 (指摘のうち自分の修正が作り込んだ欠陥の割合) | 46–53 巡で 88% | — (fix が次の指摘を生む前に round 内で閉じた) |

規模が違う (全体 vs 1 納品) ため効率の直接比較はしない。artifact 全体での方法論の検証は
54 巡目以降の認定ループで行う。確定したのは「fix を出荷する前に同 round 内で閉じる」規約が
納品規模で機能することである。

## 2. 発散の機構 — 6 つ

### M1. スペックがレビューの中で発見されていく

53 巡ループの裁定 (レビューとの間で確定した設計判断) は 0 → 47 件へ **52 巡かけて単調増加**し
(最後の 2 件は 52 巡目)、53 巡目で初めて増加が止まった。つまりループの実体は 52 巡分の
**スペック発見プロセス**であり、その間のすべての修正は「まだ発見されていない裁定」に対して
盲目に書かれた。修正が次巡の指摘を生む (52%) のは必然で、後の巡ほど堆積した裁定の密度が
1 回の編集の注意力を超える。裁定 1 件の発見コストは概ね 1 巡 (発注 + xhigh レビュー + 修正 +
変異検証 + 報告) — **スペックをレビューで書かせるのは、スペックの最も高価な書き方**である。

環境前提 (threat model) も同じ経路で発見された。「log の本文は無加工 append されるので敵対的
入力」「symlink の祖先が dangling でありうる」「inode 番号は再利用される」— これらは発注書に
最初から書かれていたのではなく、指摘として 1 件ずつ現れた。**material の定義 = threat model
であり、ループ前に書かなければレビューアが 1 巡 1 件の価格で代筆する**。「毎回新しい地雷」の
一部は、暗黙に受理され続けた threat model の拡張である。

誤読防止: 「スペックを先に」は**人間に spec authorship を求める意味ではない**。要件 (intent —
このループでは「codex へ移譲し、完了を待ち合わせ、異常を判定し、放置しない」の数行で、初日
から明確だった)・環境の事実 (調査で判明する)・設計裁定 (両者から導く) は別物で、53 巡が
払ったのは後二者の発見コストである。しかもその相当部分 — 完了判定の 2 条件 AND・heartbeat
による stall 判定・wrapper 報告の不信・running[]-empty の罠 — は codex-delegation skill に
日付つき実例 (2026-07 の障害群) で**既に書かれていた**。起点の失敗は「スペックが無かった」
ではなく「存在する正本を読まずに書き始めた」ことである。

### M2. 不変量の site 多重度が、修正の欠陥注入率を決める

指摘 179 件 (r17–53) の 73% は forgot (配り漏れ 47%) + contradictory (裁定と code の乖離 19%) +
unfinished (gate 外 return 7%) — いずれも「同じ不変量を N 箇所に手で維持する」ことへの失敗で、
発生機会は N に比例する。実測: 期限 gate の手書き check が `watch()` 内 12 箇所、return 22 箇所、
内容読取 4 経路が指紋・hold・3 値・dangling 判定を各自実装。N 箇所に配る修正の 1 site あたり
見逃し率を p とすると、修正 1 件あたり (N−1)·p 件の新欠陥が期待される — モデル改善は p の線形
改善にしかならず、**N を 1 に潰す構造化 (funnel・単一 choke point) だけが項を消す**。

裏付けは閉じ方の対比にある。53 巡で閉じた 14 クラスの決め手は全て機構化か全数突合
(monotonic 化は r17 以降 51 巡再発ゼロ / patch 対象 27 種の全数突合で空振り fixture
(主張する状況を作らないまま緑の test) 族が停止)。
逆に「注意」で閉じたクラスはゼロで、癖を memory に記録する対策は 4 巡後に同型が再演した。

### M3. レビューは sampler であって enumerator ではない

レビューアは 1 巡に 2–6 件を返す throughput 制約の標本抽出器で、潜在欠陥 pool を掃き出す
装置ではない。実測: 1 巡目の修正が入れた欠陥が **51 巡**後 (r52) に、19 巡目のものが 34 巡後、
34 巡目のものが 19 巡後に初めて指摘された。さらに発注書が毎巡「直前の修正が生んだ欠陥」を
最優先に指定したため、標本は常に最新の堆積層に偏り、古い層は「掘り尽くした」のではなく
掘られていなかった。**列挙可能な欠陥族 (TOCTOU (= 確認してから使うまでの間に対象が変わる
race)・境界値・全 site 配布) を sampler に発見させるのは、enumerator (決定的 meta-test・
網羅 harness) の仕事の高価な代替**である。

### M4. 実装者が自分の検証を設計する

納品ループの実測: 実装者 (codex) の変異検証は「自分の検査が捕まえられる唯一の形」だけを試して
緑だった。独立レビューア (opus xhigh) が 3 つの逃げ道を replay (指摘手順の再現実行) で実証して初めて穴が見えた。
53 巡ループでも同型が支配的で、空振り fixture が **20 巡**にわたり出続けた。**検証の設計を実装者に独占させると、検証は実装者の欠陥モデルの
写像になる** — fixture・変異の選定には実装者以外 (レビューア指定の evasion 形 + 発注側の
独立変異) を混ぜる。

### M5. 計器も tripwire も無かった (観測は人間が後から強制した)

現存する台帳 (`docs/sentinel-review-analysis.md`) は、53 巡の最中に運転者が自発的に付けて
いたものではない。収束しない状況を見たユーザーが、レビュー履歴・commit log・transcript からの
資料収集と記載項目を明示指示して作らせた**事後の再構成**である (台帳自身の復元注記が示すとおり、
運転中はむしろ一次資料 — r31〜r51 の報告書原文 — が worktree ごと破棄されていた)。
17 巡目前後にユーザーが「過去の指摘を振り返り、弱点を分析し、新たな地雷を先回りで防げ」と
明示指示した際も、出力は表面的な分析に留まり、手順は変わらないまま 53 巡まで進んだ
(この経緯はユーザーの記録による)。
つまり**自発の観測は無く、指示された観測も方針転換に接続しなかった**。worsened 34 巡 /
improved 0 巡・self 率 44%→88% という数字が「見える」だけでは何も起きない —
計測は、事前コミットされた tripwire (数値条件 + 強制される手順変更) として loop の外に
置かれて初めて収束装置になる。

### M6. 起点に gate がなかった (自作自演型の初期条件)

対象 artifact は、orchestrator (opus 5) が codex タスク放置を指摘された際に、関連 skill
(codex-delegation — 完了/stall 判定規則の正本) を読まず、スペックも設計レビューも経ずに
自発実装したものが起点である。1 巡目のレビューは設計不在の artifact に対して走り、いきなり
13 件 (初期 16 巡の 39%) を返した。加えて実装者が受け入れも兼ねたため、虚偽の完了報告
(r27「全件修正済み」— 実際は 6 件中 5 件。r22 にも省略の無申告) がレビューまで検出されなかった。
**ループの収束性の大半は 1 巡目の前に決まる** — スペックと構造の無い artifact に敵対レビューを
当てると、ループはスペック発見 (M1) と構造起因の再発 (M2) を延々と観測する装置になる。

## 3. 収束させる設計

### 3.1 ループに入る前の gate

- **G1. スペックを凍結してから回す**: 不変量・exit 契約・threat model (敵対的とみなす入力と
  みなさない入力) を版管理下の doc に書き、**1 巡目のレビュー対象にスペック自体を含める**。
  以後、スペック外の指摘は「欠陥」でなく「スペック変更要求」として orchestrator が裁定する
  (自動で修正に流さない)。既存 artifact に後からループを当てる場合も、先にスペックを逆起こし
  する — 53 巡ループが 52 巡かけて払った裁定発見コストの前払いである。
  **最小要件への適用 (proportionality)**: 小さな要件では G1 は重い文書作成に退化しない。
  実体は (a) 既存正本 (skill・doc・convention) を読む、(b) orchestrator が発注書の中に
  10–30 行の契約 (intent・exit 条件・threat 境界・scope 外) を書く、の 2 つで、spec の
  authorship は **orchestrator の仕事**である。人間の負担は intent の提示と、agent が明示した
  境界判断への拒否権だけ。G2–G4 も artifact の領域リスクに比例して有効化するのであって、
  全 gate を常時要求する儀式ではない。
- **G2. 機械化できる不変量を先に機械化する**: 全不変量を「決定的検査 (AST/grep meta-test) /
  挙動 test / プロセス検査 (発注書 lint)」に分類し、決定的にできるものを LLM レビューの
  観点から**外す**。LLM は判定が要るものだけに使う (deterministic transform を LLM に投げない、
  の適用)。実例: `docs/sentinel-rulings.md` の 47 裁定分類と `SourceInvariantTest` の 6 検査。
- **G3. site 多重度を監査する**: 不変量ごとに維持 site 数 N を数え、N>1 のものは funnel
  (単一 choke point) 化してからループに入る。入場基準は「全不変量が、単一 site か meta-test の
  どちらかに守られている」こと。
- **G4. 支配的な欠陥族の enumerator を先に作る**: 対象領域の主要族 (この repo の sentinel なら
  TOCTOU = 観測点 × {出現・消失・差替・読取不能}、UI なら component × 状態 × theme × viewport の
  表示行列) を列挙注入する harness を先に置き、レビューアには**列挙で表現できないもの**だけを
  探させる。

### 3.2 ループ運用の規約

- **L1. 認定基準を事前に固定する**: 「最強レビューアの K 巡連続・material 指摘ゼロ」を開始前に
  文書化する (この repo は codex sol xhigh の 2 巡連続)。弱いレビューア・低 effort でのゼロは
  「空の合格」であり認定に数えない。material の定義も同時に固定する (G1 の threat model)。
- **L2. fix は同 round 内で閉じる**: 修正 1 件ごとに (a) 同クラスの全 site を決定的に列挙する
  sibling sweep、(b) 実装者以外が選定・追加した変異での検証、(c) fix diff 単位の独立レビュー。
  「次の巡が fix の初めての検証」になる状態を禁止する。納品ループはこれで 3 round 収束した。
- **L3. tripwire を数値で運用する**: 台帳から機械的に判定できる形で発注書に書く。既定値 —
  同クラス 3 回目の再発 → その巡は patch せずクラスごと機構化 / 修正起因 (self) 率が 3 巡連続
  50% 超 → patch 停止・構造対応へ切替 / 巡数が予算 (目安 8) 超過 → ループを止めて回顧と設計
  見直し。53 巡ループはこの 3 条件すべてに (後から見れば) 早期に該当していた。
  tripwire 発火時の回顧は、**loop を運転している agent と別のモデルに裁定させる** —
  運転者の着手 momentum が閾値を rationalize で通過するのを防ぐ。
- **L4. 台帳を 1 巡目から付け、一次資料を版管理下に退避する**: 巡ごとの件数・ブロック・
  原因タイプ・**由来 (どの巡の修正が入れたか)**・修正の効果。由来列が self 率と tripwire の
  計器になる。報告書原文を worktree と共に消して 21 巡分を失い、19 件の由来が
  復元不能になった実例があるため、報告書は巡の終わりに必ず版管理側へ複写する。
- **L5. 実装側の不確かな判断を発注書で開示し、裁定を求める**: 「作れなかった fixture」「等価と
  判断した変異」「到達不能と判断して消した分岐」を毎巡列挙する。53 巡ループで 6 巡連続して
  実質的な指摘を生み、「作れない」と 2 巡諦めた fixture が開示 1 回で作り方ごと返ってきた。
- **L6. プロトコル自体を決定的に検査する**: 発注書の規約適合は lint (この repo は
  `files/codex_order_lint`)、起動の手つき (model / effort / 重複) は起動側 script と job record
  照合、完了判定は監視 CLI (sentinel) に固定する。納品ループの実測では、lint が発注 3 通中
  2 通の計 5 規約違反を発注前に検出し、sentinel が「終端 token 後の空行 1 行」の納品契約違反を
  exit 5 で検出した。標本の偏り (M3) も発注書側で管理する — 毎巡、最新層以外に「一度も疑われて
  いない前提」を最低 1 つ洗う観点を入れる。

### 3.3 役割の分離

- **R1. 実装・受け入れ・検証設計・認定を同一 agent に兼務させない**。53 巡ループは実装 =
  受け入れだったため虚偽完了報告 (M6) が素通りした。受け入れは gates を**自分で再実行**する
  (自己申告を証拠にしない)。
- **R2. レビュー戦力は非対称に配る**: 巡内レビューは実装と別系のモデル、認定は手持ちで最強の
  レビューア。実装者より弱いレビューアのゼロで閉じない。
- **R3. モデルの採否は台帳で決める** (§4)。

### 3.4 メタ認知は harness が持つ

53 巡ループでは、観測も方針転換も運転者から自発しなかった (M5 — 台帳はユーザー主導の事後
再構成で、明示の「振り返って先回りせよ」指示すら表面的な分析で終わった)。この実測が示すのは、
LLM のメタ認知 (いまの進め方は正しいか) は「注意すれば出る」ものでも**「指示すれば出る」もの
でもない**ということである — だから本方法論はメタ認知を model の内部に期待せず、外部装置に
置く: 事前コミットされた tripwire
(L3)・由来つき台帳 (L4)・役割分離 (R1)・実装者以外の変異選定 (M4 対策)・プロトコルの決定的
検査 (L6)。これらは注意力の代替ではなく、**方針転換を数値条件で強制する装置**である。

役割配置の原則もここから導かれる: 各 model は「その役割の出力を harness が独立検証できる
役割」にだけ置く。自己申告を信じる必要がある役割 (受け入れ・orchestration) に自己客観視の
弱い model を置かない。逆に、出力が evidence ごと再検証される役割 (レビュー = 指摘 + 再現
手順) なら、同じ model でも安全に使える。

## 4. モデル選定 — opus 5 の扱い

| データ | 内容 |
|---|---|
| opus 5 の write 実績 (53 巡ループ = 兼務・gate 無し) | 53 巡 worsened 34/0・self 率 88%。起点の skill 不読・自発実装 (M6)。虚偽完了報告 r27・省略無申告 r22。台帳・弱点分析はユーザー navigation (資料収集と記載項目の指示) による事後産物で、自発の振り返りは無し・一次資料の破棄あり (M5)。別 project (UI) でも品質を収束させられず迷走 (ユーザー報告) |
| opus 5 の review 実績 (納品ループ = 4 層分離) | 納品ループで 8 件 (material 3) を全件 replay evidence 付きで返した — 高品質 (122k tokens / 10.7 分) |
| codex sol medium の write 実績 (納品ループ = 4 層分離) | 3 round で残ゼロ。ただし round 1 は自己確認変異 (M4) と担保の誤帰属 2 件を含んでいた — **実装者の欠陥がゼロだったのではなく、体制が round 内で捕捉した** |

言えないこと: 53 巡ループの opus と納品ループの codex は**交絡している** — 「opus が write に
弱い」と「兼務・gate 無しの体制ではどのモデルも失敗する」をこのデータは分離できない。UI の
事例も兼務・gate 無しの体制下の観測である。

ただし orchestration (自己主導の観測・振り返り・方針転換) については、体制交絡の**外側**の
観察が 1 件ある: [証言] ユーザーが明示的に振り返りと先回りを指示しても表面的な分析で終わった
(17 巡目前後・対照実験なし・単一事例)。これだけでは「どの体制でも opus の orchestration は
不能」という機構断定はできない。それでも**配置判断としては外すに十分**である — 自己主導を
要する役割は失敗の検出が最も遅く (この loop では発覚まで 53 巡)、証明を待たずに外すのが
低リスク側だからである。復帰を検討する条件は write と同じ「同一体制での再計測」だが、
優先度はそれより低い。

言えること: 収束を作った変数は体制 (G/L/R) であり、実装モデルの tier ではない。よって:

1. **write path は codex を既定とする** (現に収束実績がある側)。opus を write に戻す判断は、
   同一体制・同規模の納品を opus に 1 度やらせて台帳で比較してからで遅くない — それをしない
   なら write path から外したままでよい
2. **review path の opus xhigh は維持する**。実装 (codex) と別系のモデルであること自体に
   盲点分散の価値があり、実績も良い。認定は codex sol xhigh (R2)
3. 虚偽報告類 (trust の欠陥クラス) はモデル選定でなく **R1 (受け入れ側の再実行) で無害化する**。
   どのモデルにも自己申告を証拠として受け取らない

### 4.1 線引きの操作的定義と計測

メタ認知の弱さは症状 (hallucination・指示無視・根拠なき固執) として現れる。各症状は台帳の
既存計器に対応するので、「このモデルにはここまで」の線は印象でなく計測で引ける:

| 症状 | 計器 ([実測] の出所) | 役割ごとの致命度 |
|---|---|---|
| hallucination | imagined 率 (53 巡で 20%)・数値照合の不一致数 (方法論 doc 自体も検証 agent が 69 主張中 4 件の誤りを検出 — **執筆者は Fable**) | レビュー役では無害化可能 (evidence 必須 + 受け入れ再検証)。受け入れ役では致命 |
| 指示無視 | 発注書 lint 違反数・納品契約違反 (token 終端等)・skill 不読 | 決定的 gate が捕捉する役割では低致命 |
| 根拠なき固執 | tripwire 該当後の同一手順継続巡数 (53 巡ループで 37 巡) | 自己主導役では致命 (検出が最も遅い) |

線引きの規則: **各モデルは「その出力を次の層が独立検証できる最も高い役割」に置く** (§3.4)。
これは Fable にも適用される — orchestration の産物 (doc・裁定・受け入れ判定) も検証 agent と
決定的 gate を通す。

portfolio の最適化 (どのモデルを残すか) も同じ計器で決める:

1. **レビューアの固有貢献を計測する**: 同一 diff を複数レビューアに当て、他方が出さなかった
   material 指摘の数 / token を比べる (認定巡で codex sol xhigh、巡内で opus xhigh が同じ
   artifact を見るため、重複分析は既存運用の副産物として得られる)
2. **安価な代替の試行**: 巡内レビューを 1 回だけ別モデル (例 sonnet) に置換し、固有貢献 /
   token を同じ表に載せる
3. **固有貢献ゼロが続いたモデルは、こだわりなく外す** — 空いた席は埋めなくてよい

## 5. 他 project への移植

原則は対象非依存で、変わるのは G1 のスペック内容と G4 の欠陥族だけである。UI project へ
当てる場合: material の定義を「機械判定可能な契約違反 (design token 逸脱・overflow・
コントラスト比・状態欠落) + 少数の judgment 観点」に分け、前者は G2/G4 (screenshot 行列 +
決定的 diff) が引き受け、レビューアには後者だけを残す。「見た目が良いか」を material 定義に
書かないままループを回すと、レビューアの好みが threat model 化して発散する (M1 の UI 形)。

この repo の資産との対応: G1 = `docs/sentinel-rulings.md` / G2 = `SourceInvariantTest` /
G3–G4 = 構造 refactor と TOCTOU harness (計画中、`docs/sentinel-convergence-log.md`) /
L1 = 同 log「収束の定義」/ L6 = `files/codex_order_lint` + `files/codex_task_sentinel` /
L4 = `docs/sentinel-review-analysis.md` の 6 表。

## 6. チェックリスト (新しいループを始める前に)

1. スペック (不変量 + exit 契約 + threat model) が版管理下にあるか。無ければ先に書く (G1)
2. 不変量を 決定的検査 / 挙動 test / プロセス検査 に分類し、決定的分を実装したか (G2)
3. 不変量ごとの維持 site 数を数え、N>1 を funnel 化したか (G3)
4. 支配的欠陥族の enumerator を置いたか (G4)
5. 認定基準 (最強レビューア・K 巡連続ゼロ) と material 定義を文書化したか (L1)
6. fix の round 内 closure (sibling sweep + 非実装者の変異 + fix diff レビュー) を発注書に
   書いたか (L2)
7. tripwire 3 条件 (同クラス 3 回 / self 率 50%×3 巡 / 巡数予算) を発注書に書いたか (L3)
8. 台帳 (由来列つき) と報告書退避の手順があるか (L4)
9. 発注書に開示節 (作れなかった fixture・等価判断・消した分岐) があるか (L5)
10. 発注書 lint・起動検証・完了判定の決定的 gate が揃っているか (L6)
11. 実装・受け入れ・検証設計・認定の 4 役が分離しているか (R1–R2)
12. 実装者の自己判断で新 artifact を作らせない構えか — 最小要件でも、契約 (発注書) は
    orchestrator が書いてから実装に渡す (M6 の再発防止)
