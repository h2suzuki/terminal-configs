# レビューと受け入れの運転規約

LLM に実装させた道具をどう受け入れるかの規約。5 項目。[バグ回避] = 作り込みを起こさない手順、
[バグ検知] = 起きた後に捕まえる機構。根拠・経緯・旧版は `docs/adversarial-loop-meta-evaluation.md` と git 履歴。

1. **実装前に発注側が書く**: [バグ回避] 契約 (目的・用途内外・入出力と exit・不変条件・所有点、10〜30 行)。
   書けなければ発注しない。環境の実態を先に測り、次に既存の正本を読む。[バグ検知] 受け入れ test と固定 4 変異
   (不正入力の置換 / 境界の反転 / 出力 marker・counter の増減 / 正規化の除去)
2. **構造を先に決める**: [バグ回避] 不変量が複数 site に配られる、または状態 × 遷移を列挙できないなら、
   funnel か enumerator を先に作るか用途を縮小する。局所 patch は発注しない
3. **レビューは read-only の品質推定**: [バグ検知] 道具本体だけを渡し (発注書・過去の指摘・裁定は
   見せない)、correctness と要件に効く指摘だけを求める。finding は class でまとめ、処置は
   仕様縮小 → 削除 → 既存 primitive への集約の順。新機構は fix でなく別発注
4. **触る量を減らす**: [バグ回避] fix diff ≤ 100 行、発注書 ≤ 60 行、レビュー単位 ≤ 400 行。自己申告と
   test 本数は証拠にしない
5. **採否は用途内 P0 と変異の生存数で決める**: [バグ検知] 生存 0/4 が受け入れ条件。緑と指摘総数は補助。
   直さない指摘は転記しない — reviewer の報告書 file がそのまま記録

凍結 (2026-08-26): この規約への追記は禁止し、削除だけを許す。足したいものが出たら、先に何を消すかを書く。
