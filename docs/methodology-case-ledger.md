## 巡 7 — 発注側の仮説は反証された (2026-08-26)

巡 7 は「発注側が契約をコードで書いて渡せば、仕様側の欠落が減る」という仮説の検証だった。
事前に 4 つの予想を宣言し、diff round の結果と突き合わせた。**結果は反証**。

| 予想 | 結果 |
|---|---|
| 初回レビューの指摘は 3 件以上 | **当たり** — findings 6 |
| **中 severity が 2 巡以内に 0** | **大きく外れ** — **高 2 件**が出た (前巡は中 1) |
| 指摘の由来から「仕様側の欠落」が半分以下に | **外れ** — 高 1 件と中 1 件が発注側の契約由来 |
| 変異生存数が単調減少 | **測定自体が信用できなかった** (下記) |

### 巡 7 の全体 round — findings 8。巡 6 の 5 件より**増えた**

| 巡 | diff round | 全体 round | 合計 |
|---|---|---|---|
| 6 | 2 | 5 | **7** |
| 7 | 6 | 8 | **14** |

**倍に増えた。** 内訳には巡 7 が新設した構造に由来するものと、5 巡以上生き延びていた在庫の
両方が含まれる。とくに重いもの:

- **ELF binary を target にすると、byte 同一 revision で false DIFF**。base は絶対 temp path、
  target は相対 path で argv[0] が渡るため、argv[0] の長さや dirname を使う target が差分になる。
  shebang script では kernel が argv[0] を置き換えるため露見せず、binary でのみ出る
- **`--repo` に subdirectory を渡すと、別々の 2 file を比較して verdict を出す**。
  `validate_target` は `--repo` 基準、`git show` は repository root 基準で解決するため
- **corpus の file 名に改行があると、報告行数と件数表示が食い違う** (`DIFF` 行 5 に対し
  `2 difference(s)`)。警告行の偽造も同様に可能
- **宣言域内の `--timeout 2147484` が uncaught 例外で exit 1** — 「差分あり」と同じ exit code
  になり、呼び手が区別できない

### 反証の中身

**(1) 契約で直した欠陥が、別の場所で同じ形に再発した**。基準版の乱数を「親 directory 名」から
「file 名」へ移した結果、target が `Path(__file__).stem` / `splitext` のように**名前を分割して
使う**と正規化が効かず、**byte 同一の revision で false DIFF が出て stdout も再現しない**。
巡 2 で直した F3・F4 と**同じ class**である。**発注側が I5 (入力に無い値を出力へ混ぜない) を
書いたのに、実装の自由度がそれを別の形で破った。**

**(2) 契約 module への依存が、配備先で selftest を常に赤にした** [発注側が再現]。
生成 test が `drafts.ab_probe_contract` を import するが、`drafts/` は gitignore で repo に無い。
`files/claude_ab_probe` は installer が `/usr/local/bin` へ deploy するので、
**配備された道具の `--selftest` は必ず失敗する**。単独配置で exit 1 を実測。

**(3) 新しい品質指標が自己申告で、しかも誤っていた** [発注側が再現]。報告書は
「71 変異中 71 kill・生存 0」と書いたが、`print_element_diff` の 249 行に変異を当てると
**selftest は exit 0 のまま = 生存**。発注書は「変異は自分で選ばず機械列挙で決めよ」と
書いたが、**その機械列挙を実装者が書いた**ため、方法論 M4 (検証の設計を実装者に独占させると
検証は実装者の欠陥モデルの写像になる) がそのまま再現した。

### この反証から言えること

- **契約のコード化は「解釈の相違」を消すが、「書き落とし」も「実装の自由度」も消さない**。
  I5 という正しい不変条件を書いても、それを満たす実装のうち別の穴を持つものが選ばれた
- **測定を実装者に設計させた時点で、その測定は品質の指標にならない**。変異の生存数という
  指標自体は有効でも、**誰が変異集合を決めるか**が結果を支配する
- **仮説を事前に数字で宣言したことは有効だった**。「中 severity が 2 巡以内に 0」と先に書いて
  いたので、高 2 件という結果が言い逃れなく反証になった

## ケース 1 の結論 (2026-08-25)

**ケースは問いに答えた。巡を続けても新しいことは分からない**ので、ここで止める。

### 何が分かったか

1. **diff だけを渡すレビュー loop は、自分の尾を追っていた**。指摘 5 → 3 → 2 → 2 の減衰は
   「変更量を小さくすれば指摘は減る」を測っていただけで、その極限 (変更 0) は自明に 0 件。
   中 severity は 3 巡とも 1 件で**減衰ゼロ**だった
2. **在庫欠陥は 0 件ではなく 5 件あった**。5 巡の diff round が 1 件も触れず、
   **全体 round 1 巡で 5 件出た**。「在庫 0 件・指摘 100% が直前 fix 由来」は測定結果ではなく
   レビュー設計の恒等式
3. **注入源は実装ではなく発注書だった** — 巡 3・4・6 の近因はいずれも発注書の
   under-specification。コードは毎巡直っているのに、**仕様を書く工程だけが変わらなかった**
4. **根拠のない裁定がバグを 4 巡守った** — 「7b は正しい」は測定なしの宣言で、test と
   全数列挙表がそれを仕様として固定していた
5. **点で直すと一般形が残る** — 巡 2 で `argv[0]` の basename を直したが、真因
   「基準版を元の場所から動かして実行する」は残り、全体 round が F3 / F4 として再発見した

### なぜここで止めるか

残る 5 件は**在庫欠陥**であって、fix が注入したものではない。これを fix queue に入れると
**loop が食う欠陥の母集団が変わり**、「この loop は収束するか」という問いの測定対象が入れ替わる。
巡 7〜10 を使っても測れるのは「既知のバグ 5 件を直すのに何巡かかるか」で、ケースの問いではない。

### 道具そのものの状態

`claude_ab_probe` は **使える状態にない**。false negative (F1) を抱えており、
「差分なし」の報告を信用できない。commit / merge / 配備はいずれも未実施。

### 巡 6 のレビュー設計を、結果を見る前に決めておく (2026-08-25)

診断が示したとおり、diff だけを渡すレビューは**在庫欠陥を構造的に見つけられない** (実際 1 件が

### effort max の独立診断が、発注側の自己診断を反証した (2026-08-25)

発注側は「毎巡『点』を書いて『規則』を書いていない」と自己診断していた。独立診断はこれを
**主因ではない**と判定し、より重い 3 点を出した。発注側が**自分で再現・確認した**結果を記す。

**(1) 「在庫欠陥 0 件・指摘 100% が直前 fix 由来」は測定でなく恒等式**。退行レビューには
発注書だけを渡しており、発注書は直前 fix の記述そのもの。**レビューアの注意は構成上そこにしか
向かない**。発注側はこの数字を「道具は元から正しい」の根拠として繰り返し使ったが、
**由来分布は測定結果ではなくレビュー設計の写像**だった。

**(2) 中 severity は 3 巡とも 1 件で減衰ゼロ** (巡 2 中1/低4・巡 3 中1/低2・巡 4 中1/低1)。
発注側は合計 5 → 3 → 2 を「収束方向」と報告したが、**減っているのは低の尾だけ**で、それは
変更量に追随している。収束していれば真っ先に severity が落ちるはずが、落ちていない。

**(3) 在庫欠陥が実在する — しかも発注側の裁定がそれを「正しい」と凍結していた**。
`run_command` は timeout 時に kill 時点までの部分出力を採る。**発注側の再現実測**: 少しずつ
書き続けるプログラムを timeout 0.25 秒で 8 回走らせると捕捉長は 943 が 7 回・952 が 1 回。
**同一プログラム 2 回の `changed_elements` が `['stdout']` を返す** = **同一コードが差分として
報告される**。つまり発注側が何度も書いた「同一版どうしなら差分 0 件」は**timeout が起きない
corpus に限って成立する主張**だった。
そして巡 4・5 の発注書は裁定で「**7b (両側 timeout・出力相違) を差分に数える挙動は正しい**」と
宣言し、test と全数列挙表で固定していた。**測定を伴わない裁定が、バグを仕様として 4 巡守った。**

**帰結**: 「裁定」は発注側が探索空間を狭める道具だが、**根拠を伴わない裁定は凍結された推測**で
あり、レビューアはそこを触れない。裁定は巡 4 で 8 項目・巡 5 で 9 項目と単調増加していた。
今後の裁定には**再現手順を添える**こと。添えられないなら裁定にしない。

### 本ケース限りの運転許可 (2026-08-25)

ユーザーが「今日は、最大 10 巡まで自走してください」と述べ、直後に
「**私は一般的な上限については述べていません。今回の収束について、様子を見るために許可した
だけです**」と補足した。したがってこれは **本ケース 1 件に限った運転許可**であり、

- **方法論の 5 巡規定は変えていない**
- **他ケースの上限にもならない**
- **5 巡以内収束という当初の成功基準に対する判定は「達成不能」のまま据え置く** — 事後に
  上限を動かして達成扱いにすると、測っている対象が消える

許可の目的は「実際には何巡で収束するのか」を観察することである。

### 収束判定 — 5 巡以内は達成不能

#### 巡 1 の指摘 (いずれも発注側が再現)

**指摘 1 (高) — 同一版どうしの比較で差分が出る**。基準版を temp file から実行する際、
file 名が `base-<乱数>-<元の名前>` になるため `argv[0]` の basename が変わる。argparse の
既定 prog と、この repo の `PROG = os.path.basename(sys.argv[0])` 慣用が**自分の名前を
出力に載せる**ので、コードが同一でも stderr が食い違う。正規化は**絶対 path しか置換していない**
ため発火しない。実測: `--base HEAD --target files/codex_task_sentinel` (無変更) で
`usage: base-atcnovpw-codex_task_sentinel` と `usage: codex_task_sentinel` が差分として出、
exit 1。道具の中心的な約束 (同一挙動なら差分ゼロ) が崩れる。
dogfooding 2 が 0 件で通ったのは、`codex_order_lint` がその経路で自分の名前を出さなかった
偶然による。**由来 = 在庫** (発注書が要求した pin 6 点にこの形が無く、実装側の test も覆えていない)

**指摘 2 (中) — 両側が同じく timeout した項目を差分として数える**。実測: `--timeout 0.01` で
同一版を比較すると `changed: timeout` / `base timeout: timeout` / `target timeout: timeout` と
**同じ値を並べたまま DIFF** と印字し、差分 1 件・exit 1 になる。「測れなかった」と
「挙動が変わった」を同じ数に混ぜている。**由来 = 在庫**
