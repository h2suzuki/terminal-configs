# Jev 文脈判定 hook (jev_context_gate)

エージェントが既存ファイルの途中に書き足した内容が置いた場所の文脈に合っているか、新しく加えたファイルがその場所に置く完成した内容かを、コミットの直前に Jev で判定する hook です。合わないと判定した変更はコミットを止めます。判定するのはセッションに接続済みの Jev MCP サーバー (`jev serve`) で、hook はその受付口のツール `context_gate` を呼びます。判定の本体は `files/jev_context_gate.py`、受付口は `files/jev`、テストは `tests/jev_context_gate.test.py` と `tests/jev.test.py` です。

## 1. 目的

文脈に合わない書き足しは、文書でもコードでもテストでもバグの埋め込みです。例えば、利用者向けの「初回の認証・接続」の節に、保守者向けの同期規則や権限の対応付けを書き足すと、目次と文章構成が崩れます。関数に別の責務を足す、テストに名前と無関係な検査を足すのも同じ種類の誤りです。要件や設計の下書きを読み手向けに蒸留せず、そのままリポジトリ直下に新しいファイルとして置くのも、置き場所と中身の誤りです。

この hook は、そうした書き足しをコミットの時点で機械的に止め、エージェントに削除か移動を求めます。

## 2. 対象範囲

| 対象 | 扱い |
|---|---|
| 既存ファイルの途中への追加 (文書・コード・テスト) | 判定する |
| 既存ファイルに新しい見出しを足す追加 | 追加行の判定に加え、新しい節を同じ階層の節と比べて判定する |
| 新規ファイル | 置き場所と完成度を判定する (新規ファイルの問い)。中身は要約せず、冒頭と形、同じディレクトリにある既存のファイル名で判定する |
| 削除だけの変更 | 判定しない |
| Jev が使えない環境 | 判定を省略し、その旨を利用者に表示する |

## 3. 仕組み

### 3.1 発火点

Claude Code と Codex の PreToolUse hook (`mcp_tool` 型) が、Bash (Codex では `exec_command` も `Bash` として一致) の呼び出しを、接続済みの `jev` サーバーの `context_gate` に渡します。サーバーは `git commit` のときだけ判定し、それ以外は API を呼ばずに空の結果を返します。Edit・Write・`apply_patch`・`sed` など、どの経路で書いた変更も最後はコミットを通るため、ここを判定の関門にしています。

判定の対象は、コミットに入る差分です。`git commit -- <path>` と `git commit -a` は作業ツリーと `HEAD` の差分、パスなしのコミットはステージした差分、`--amend` は `HEAD^` からの差分を見ます。

### 3.2 判定の流れ

1. 差分を hunk に分け、追加行を piece に切ります。Markdown は段落ごとに切り、見出しは直後の段落に、コードブロックは直前の段落に付けます。コードは空行で切らず hunk ごとに 1 つの piece にします (関数の途中の切れ端には、判定できる場所の文脈がないため)。どちらも 1500 字を超える分は切ります。
2. piece ごとに、ファイルと場所の文脈を機械的に組み立てます (3.3)。
3. 同じ場所に続く piece は同じ問い合わせにまとめます。問い合わせはファイルごとに分け、上限を超える場合だけ同じ場所の中で分けます。
4. 同じサーバーの Jev セッションで判定します。hook はプロセスを起動せず、サーバーが git の差分を読みます。
5. 新しいファイルは piece に切らず、ファイルごとに 1 回問い合わせます。
6. どれか 1 つでも判定が閾値を下回れば、コミットを拒否します (3.4)。

### 3.3 Jev に渡す文脈

Jev の精度は、質問の言い回しより「どういう背景で、どういう種類のファイルの、どの場所に、何を書き足したか」を短く明確に渡せるかで決まります。そのため、次の欄を LLM を使わずに埋めます。

| 欄 | 中身 | 作り方 |
|---|---|---|
| `form.background_of_change` | 変更の背景 | コミットメッセージの件名と本文の先頭 |
| `form.file_kind_and_role` | ファイルの種類と役割 | 題名、冒頭の段落、文書全体の形 (行数・表・箇条書き・コマンドブロック・段落の長さ・外部リンク数を数えて英文にしたもの)。コードとテストではファイル冒頭の docstring |
| `hunks[].place_and_its_purpose` | 書き足した場所とその目的 | 見出しの階層と、それぞれの節の最初の段落 (コードでは囲む関数・クラスとファイルの docstring) |
| `hunks[].style_of_this_place` | その場所の書き方 | 変更前の同じ節の形を数えた文 (新しい節なら文書全体)。コードとテストでは変更前の定義の一覧 |
| `pieces[].what_the_edit_adds` | 書き足した内容の形 | 追加行の形を数えた文 |
| `pieces[]` の前後と本体 | 根拠 | 前後 6 行と追加行 |
| `new_files[]` | 新しく加えたファイル | パス、題名と冒頭の段落 (コードではファイル冒頭の docstring)、ファイル全体の形、冒頭 3000 字、同じディレクトリにある既存のファイル名 (40 件まで、ディレクトリは末尾に `/`)。ディレクトリが新しいときは、既にある最も近い親ディレクトリのファイル名 |
| `new_sections[]` | 新しい節と同じ階層の前後の節 | 行数・段落・表の行・コードブロック・外部リンク・小見出しの数と本文 (新しい節は 5000 字、前後の節は 1200 字まで) |

日本語の本文は訳さずにそのまま渡します (付録 A)。

### 3.4 質問と判定規則

- **配置の問い** (piece ごと、Jev の noul): 書き足した内容は、その節を目的どおりに読みに来た人が求めるものか。合わない例として、保守者向けの規則 (原本ファイル・同期・実行するテスト・ツール間の権限の対応付け)、調べた根拠・確認日・外部文書への注意書き、周りより細かい参考情報、別の見出しに属する内容を具体的に挙げています。
- **節の書きぶりの問い** (新しい見出しごと、noul): 新しい節は、同じ階層の節と同じ書き方と詳しさか。表・多数の外部リンク・確認日・注意書き・仕組みの説明が並ぶ節は合わないとしています。
- **新規ファイルの問い** (新しいファイルごと、noul): そのファイルは、同じディレクトリに置かれているものと同じ種類の、読み手向けに仕上がった内容か。合わない例として、下書き・メモ・要件や設計の覚え書き・計画・セッションの記録・レビュー報告・会話の写しを整理せずに置いたもの、文書を docs ディレクトリに置くリポジトリで直下に置いた長い文書を挙げています。
- **判定**: いずれかの確率が 0.5 未満なら拒否します。拒否の文面には、ファイル名と行、場所、確率、どの問いで落ちたか、書き足した行 (新しいファイルでは先頭) の冒頭を載せます。

### 3.5 大きな変更の扱い

piece の追加行は 1500 字、1 回の問い合わせの state は 12000 字までに分けます (Jev の上限は state と最長の質問で 32k トークン)。長い新しい節は要約せず、節の書きぶりの問いで同じ階層の節と比べて判定します。

## 4. 失敗したときの振る舞い

次の場合は判定を省略してコミットを通し、`systemMessage` で「Jev の文脈チェックを省略しました (理由: …)」と利用者に表示します。

- 判定の本体がサーバーに配備されていない
- API キーが無い、認証・通信・レート制限のエラー (Jev が返すエラーの本文を理由に載せます)
- 25 秒以内に応答が無い (`JEV_CONTEXT_GATE_DEADLINE` で変更可)
- サーバーが先の失敗を覚えている間 (下記)
- 応答を読めない、判定が欠けている

`jev` サーバーが未接続のとき、またはツールがエラーを返したときは、Claude Code と Codex が hook の失敗として扱い、コミットは止めません。

サーバーは失敗を覚え、同じ問い合わせを繰り返しません。API がキーを拒否した (401・403) ときは、保存したキーのファイルが変わるまで問い合わせずに省略します。レート制限・サービス障害・通信エラーのときは、30 秒から 30 分まで倍々に延ばした待ち時間の間、問い合わせずに省略します。`jev api-key set` でキーのファイルが変わると、サーバーは次の呼び出しでキーを読み直します。

## 5. ログと有効性の評価

hook は判定ごとに 1 行の JSON を `~/.claude/hooks/state/jev_context_gate/log.jsonl` に追記します (`JEV_CONTEXT_GATE_LOG` で変更可)。ログに書けなくても hook の動作は変わりません。

記録する主な項目は、日時、セッション、リポジトリ、コミットの件名、結果 (拒否・許可・省略) と省略の理由、Jev のモデル名とトークン数、所要時間、閾値と質問の版 (`QUESTION_VERSION`)、判定したサーバーのプロセス番号 (`server_pid`) です。piece ごとにファイル・行・種類・場所・書き足した内容の形・追加行のハッシュと冒頭・確率・合否を、新しい節ごとに見出し・確率・合否を、新しいファイルごとにディレクトリ・確率・合否を記録します。

ログから次のことを確かめます。

- **誤った拒否**: 拒否の後、同じファイルが内容を変えずにコミットされたもの。閾値か質問の見直しが必要な候補です。
- **見逃し**: 後から人が削除・移動した書き足しのうち、許可されていたもの。追加行のハッシュで元の判定をたどれます。
- **省略の多さ**: 省略の理由ごとの件数。多ければ、Jev の設定か通信を確かめます。
- **閾値の妥当性**: 許可と拒否の確率の分布。質問を変えたら `QUESTION_VERSION` を上げ、版ごとに比べます。
- **常駐サーバーでの判定**: 同じセッションのコミットで `server_pid` が変わらないこと。変わるなら、判定のたびにサーバーが起動し直されています。

## 6. 登録と設定

| クライアント | 登録先 | 設定 |
|---|---|---|
| Claude Code | `files/claude_managed-extensions.json` の PreToolUse `Bash` | `mcp_tool` (`jev` / `context_gate`)、`if: "Bash(git *)"`、コマンド文字列を渡す、タイムアウト 60 秒 |
| Codex | `files/codex_config.toml` の `[[hooks.PreToolUse]]` (`^Bash$`) | `mcp_tool` (`jev` / `context_gate`)、`tool_input` をそのまま渡す、タイムアウト 60 秒 |

判定の本体 `files/jev_context_gate.py` は、導入スクリプトが `jev` の実行環境 (`/usr/local/lib/jev/`) に配備し、サーバーが読み込みます。Jev の API キーの設定は [Jev の利用手順](typesafe.md) を参照してください。

## 7. 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| git の pre-commit hook | git から外部サービスを呼ばない方針のため。git に入れるのはローカルで完結するツールだけにする |
| hook が自分で `jev serve` を起動して問い合わせる | セッションに接続済みのサーバーを使わず、コミットのたびにプロセスの起動・プロセス間通信・MCP の初期化を行う。失敗の記憶もキーの状態も残らず、CLI を直接呼ぶより重い |
| 編集ごと (Edit・Write) の判定 | 書きかけの状態まで止めてしまい、Bash での編集も捕まえられない |
| 書き足した README のコミット自体を止める | README の更新は正当。問題は文脈に合わない内容 |
| LLM (Haiku など) で英訳・要約してから渡す | 実験で精度が上がらなかった (付録 A)。`claude -p` は 1 回 11〜18 秒かかり、hook から LLM を呼ぶことは `deny_llm_call_in_hook.py` の方針 (同期の hook を止めるか、非同期では介入に間に合わない) にも反する |
| 編集理由 (コミットメッセージ) とファイルの役割の一致を問う | 機能のコミットが README を 1 行直すような正当な変更を誤って止めた |
| 理由の選択肢 (choice) での判定 | 確率の判定と食い違い、明らかな書き足しを「合う」と答えた |
| 文書全体を添付する | 精度が上がらず、わずかに下がった |

## 付録 A: 設計の根拠にした実験

2026-09-23 に、このリポジトリの README.md の実際のコミットで、Jev (`jev-1.13.0`) の判定を比べました。

- **止めるべき編集 (5 件)**: `4d590b7`・`25130db`・`a2f95c7`・`2cade7f` (「初回の認証・接続」への保守者向けの説明の追加) と `dde00bb` (表・根拠リンク・確認日を詰め込んだ長い新しい節)
- **通すべき編集 (12 件)**: `c222ab7`・`61fd268`・`e16b754`・`6baa8f1`・`1d07e17`・`2b6eb12`・`5058a75`・`6cd6bbb`・`4212cf4` など、README の整理と短い手順の追加
- **指標**: 通すべき編集の最低点から、止めるべき編集の最高点を引いた差 (マージン)。コミットの点は、その piece と新しい節の点の最小値

| 入力の形 | 止めるべき編集の最高点 | 通すべき編集の最低点 | マージン |
|---|---|---|---|
| 最初の実装 (見出しの階層と目次のみ、編集理由の問いあり) | 0.79 | 0.23 (編集理由の問いで誤拒否) | マイナス |
| 判定基準を具体化 (機械的な前置きなし) | 0.24 | 0.54 | +0.30 |
| **機械的な前置き + 具体化した判定基準 + 節の書きぶりの問い (採用)** | **0.25** | **0.72** | **+0.47** |
| 上に英訳を加える | 0.22 | 0.70 | +0.48 |
| 上に文書全体を加える | 0.28 | (未測定) | — |
| 前置きを LLM が書いた場合 | 0.31 | 0.85 | +0.54 |

- 判定基準の具体化が見逃しを減らし、機械的な前置きが誤った拒否を減らしました。
- 長い新しい節 (`dde00bb`) は段落ごとの判定では 0.57 で抜けましたが、節の書きぶりの問いで 0.23 と捕まえられました。
- 同じ問い合わせを繰り返したときの揺れは 0.01 程度でした。一方、piece を 1 つだけで送ると、同じ hunk の他の piece と一緒に送った場合より点が下がりました (0.72 → 0.52)。そのため、同じ hunk の piece はまとめて送ります。
- 英訳と LLM による前置きは、機械的な前置きに比べて差が小さく、hook から LLM を呼ぶ遅さ (1 回 11〜18 秒) に見合わないと判断しました。

**限界**: 評価したのは README の日本語の変更だけです。コードとテストの判定、新しい節の問いの誤拒否率は、運用のログで確かめます (5 章)。
